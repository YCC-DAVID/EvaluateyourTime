# AI 时间利用管理 App：产品与开发规格

> 版本：v0.1 · 讨论整理稿  
> 更新：2026-11-24  
> 状态：准备开发；本文描述目标行为，不表示功能已经实现。  
> 项目名称待定。面向个人、朋友及家庭使用，计划开源。

## 1. 项目定位

构建一个支持电脑和手机的个人时间管理工具，以轻量记录、设备使用参照、目标管理和 AI 反馈，帮助用户理解自己的时间去向，并逐渐改善时间安排。

核心原则：**工作认真工作，娱乐尽兴娱乐，休息安心休息。**

我们评价的是时间是否被主动、合理地使用，以及是否推进当前目标。不能简单地把工作视为高分、娱乐视为低分；也不能把坐在电脑前的时长等同于有效工作。

### 1.1 典型用户

- 研究生、研究人员、程序员及其他脑力工作者。
- 想减少拖延、无意识刷手机，同时保留运动与休息的人。
- 不愿维护复杂生产力系统，希望每次只花少量精力记录的人。
- 希望自行选择 AI 服务、同步后端并拥有数据的开源用户。

### 1.2 核心价值

1. 记录足够轻松，支持事后补录。
2. 用设备使用情况提供参照，减少含糊的自我评价。
3. 每段最多两三个问题，不做审问式核对。
4. 评分理由清楚，用户能修正，系统能学习偏好。
5. 评价和当前阶段目标有关，同时保护必要的恢复时间。
6. 默认本地保存，可选同步，不强制使用项目运营者的服务器。

### 1.3 第一版不承担的目标

- 证明用户是否诚实，或精确测量人的注意力。
- 无感监控 iPhone 中其他 App 的内容或触摸手势。
- 持续录屏、持续上传原始传感器数据。
- 通过聊天订阅凭据实现通用 API 转发。
- 自动替用户决定人生优先级。
- 为每个平台同时实现所有同步服务。

## 2. 产品主流程

1. 用户选择时间段。
2. 通过文字、语音或图片描述做了什么。
3. AI 整理活动与时间分配草稿。
4. 用户对照设备使用情况，确认分类时长或百分比。
5. 最多补充一个有必要的澄清问题。
6. AI 给出评分、简短理由和不确定项。
7. 用户确认或修改后保存。
8. 更新当天热力图和统计。
9. 在每日复盘、每周复盘时形成建议及规则调整提案。

### 2.1 示例

用户选择 14:00–17:00，输入：

> 看论文，主要想理解方法，整理了一点笔记，中间刷了会儿手机。

界面上半部分显示这一时段的设备使用参照；下半部分接收记录和答案。

| 问题 | 交互 |
|---|---|
| 做了什么、推进了什么？ | 用户输入；AI 可追问“理解核心方法／整理笔记／排除思路／尚未理解” |
| 时间大概如何分配？ | AI 生成草稿，用户调整工作、休息、必要事务、分心的分钟数或比例 |
| 手机使用主要属于什么？ | 有必要时选择“主动休息／反复分心／任务相关／记不清” |

以上是总计最多三个问题，不是在每个问题下再展开多轮问答。复杂情况允许用户主动展开详情。

## 3. 信息架构与页面

| 页面 | 主要内容 |
|---|---|
| 今天 | 当日热力图、时间轴、快速记录、有效工作预算、待补录空档 |
| 记录与编辑 | 时间段、设备参照、活动输入、分类分配、问答、评分确认 |
| 目标 | 长期目标、短期目标、DDL、进度、当前主要目标 |
| 回顾 | 日报、周报、时间分布、趋势与目标投入 |
| 设置 | 分类、个人规则、预算、AI 服务、同步、数据管理、隐私 |

### 3.1 手机交互

- 快速记录入口醒目，默认时间为上次记录结束至现在。
- 支持调整起止时间、跨午夜记录、补录历史。
- 时间轴纵向排列，支持点选编辑。
- 支持分钟与百分比互相换算。
- 先保存原始记录，AI 分析可以稍后完成。
- iPhone 的设备使用报表与主 App 问答同屏展示。

### 3.2 电脑交互

- 时间轴支持拖选时间段。
- 记录详情、设备活动摘要可以并排显示。
- 支持粘贴图片、拖入附件。
- 便于批量补录、检查目标和查看一周趋势。
- 支持连接 ActivityWatch；未安装也能使用基础功能。

## 4. 输入与记录设计

### 4.1 输入方式

| 输入 | 第一版处理 |
|---|---|
| 文字 | 首先实现，作为核心输入 |
| 语音 | 转写后允许纠正，再进入记录分析 |
| 图片 | 提取活动证据或文字，保留用户确认步骤 |

模型未必同时支持文字、语音和图片。ASR、图片理解和评分应为独立可配置能力。不能凭一张工作截图认定整个时间段都在工作。

### 4.2 初始分类

| 大类 | 示例 | 评价依据 |
|---|---|---|
| 工作与学习 | 研究、代码、写作、课程 | 投入、推进、目标相关性 |
| 运动与健康 | 打球、健身、游泳 | 是否达到锻炼意图、安排是否合理 |
| 休息与睡眠 | 午休、恢复、睡眠 | 是否得到恢复、是否满足个人需要 |
| 娱乐与社交 | 游戏、电影、聚会 | 是否主动安排、是否尽兴、是否明显超时 |
| 生活与必要事务 | 做饭、购物、通勤、沟通 | 必要性与安排合理性 |
| 无意消耗 | 无意识刷手机、拖延、反复分心 | 是否偏离原本意图 |
| 未分配或不确定 | 记不清的部分 | 保留不确定性，不自动判低分 |

用户可以增删分类或建立子类。分类不等于分数；同类活动在不同背景下可以有不同评价。

### 4.3 时间分配

- 内部以时长为准保存，百分比为派生值。
- 输入分钟或比例时，另一项即时换算。
- 显示剩余未分配时长，允许保留未知部分。
- AI 推测的时长必须标为估计，用户确认后才成为确认分配。
- 一个时间段的分类分配总和不得超过该段时长。
- 多设备证据可以重叠；主记录的墙钟时间不能因证据重叠而增加。
- 只有比例、没有具体分段时，不虚构活动发生顺序。

## 5. 目标体系

### 5.1 时间尺度

| 层级 | 默认时间范围 | 示例 |
|---|---|---|
| 长期目标 | 未来两三个月 | 完成一个研究项目、建立规律运动习惯 |
| 短期目标 | 未来一两周 | 完成关键实验、提交初稿 |
| 具体任务 | 当天或具体活动段 | 完成一组消融、阅读方法部分 |

长期、短期目标可以设置 DDL；健康和习惯类目标也可采用周期性指标而不强制设截止日期。

每个目标至少包含名称、说明、时间范围、DDL、进度、优先级、父目标和状态。进度可以是里程碑、完成数量或用户判断，不能一律用投入小时代替。

### 5.2 当前主要目标与次要事项

AI 结合以下信息提出优先级建议：

- 重要程度与长期目标关系。
- 截止日期和剩余工作量。
- 当前进度、落后程度。
- 任务之间的依赖与阻塞。
- 用户近期状态和可用时间。

用户确认当前主要目标，允许随时调整。系统说明判断依据，不能擅自把用户目标替换为自己的判断。

重要但不紧急的任务不能因缺乏紧迫性长期低分。必要睡眠、运动和恢复保留独立价值，避免主要目标无限挤占生活。

## 6. 评分与有效工作预算

### 6.1 评分维度

| 维度 | 含义 |
|---|---|
| 执行质量 | 是否认真投入；是否得到与活动相符的推进、锻炼或恢复 |
| 目标贡献 | 与当前主要目标、短期目标、长期目标的关系 |
| 安排合理性 | 是否符合计划、是否明显超时、是否挤占其他必要活动 |

采用可解释的默认规则和可版本化权重，不追求一开始就设计复杂公式。重要／紧急四象限、DDL、时间预算等作为内部管理框架；第一版不要求用户学习或选择大量理论模型。

研究探索应认可理解、验证和排除错误路线，不能只看论文页数、代码行数或可见产出。娱乐与恢复不套用脑力工作的产出标准。

### 6.2 每日有效脑力工作预算

- 默认 6 小时，属于产品初始预算，不是医学上限或人人必须完成的指标。
- 预算适用于脑力工作；其他活动单独统计。
- 以用户确认的有效投入时长累计，未分配时间不自动计入。
- 一段三小时活动中，确认工作两小时、休息半小时、分心半小时，则累计两小时有效工作。
- 执行质量与工作时长分别保存，避免对同一段分心重复扣减。
- 超过预算仍可记录，但不靠无限加时持续抬高每日评价。

两个独立指标：

```text
工作预算完成率 = 当日确认的有效脑力工作时长 / 当日工作预算
重点目标投入占比 = 主要目标的有效工作时长 / 全部有效工作时长
```

完成率可以超过 100%，展示时不得被解释为“应该每天超额”。没有工作时，重点目标占比显示无数据而非除以零。

### 6.3 个性化调整

每周参考疲劳、恢复、任务推进和用户反馈，提出小幅增加或减少预算的建议。用户确认后生效，保留生效日期。临近 DDL 的临时调整需有结束日期。

不会因为偶尔熬夜或工作很久就自动提高要求；也不会因某周状态差就认定能力下降。

### 6.4 用户改分与规则学习

用户修改时可选择：

- 仅修改本次。
- AI 理解错误。
- 分类或时长估计错误。
- 当前评分规则不合适。
- 希望以后类似情况采用同样标准。

每天检查纠正记录，必要时提出小幅规则调整。规则更新是配置与偏好学习，不是每天训练模型。保存原始分、最终分、规则版本、改动原因和来源记录。

旧评分默认保留；新规则用于后续记录。如需重算历史，必须明确标为新版本重算，不能混淆历史进步。

## 7. 引导问题设计

### 7.1 原则

- 每段总计最多两三个问题，能少问就少问。
- 先问事实，再展示初评，减少用户按分数倒推答案。
- 根据任务生成具体选项，提供记不清、混合状态及自由输入。
- 识别明显矛盾时优先给一个澄清问题，而不是增加多轮问答。
- 不声称识别了谎言，不把缺少设备证据当作低效。

### 7.2 例子

| 活动 | 有用的问题 |
|---|---|
| 读论文 | 理解了核心方法、形成笔记、排除思路，还是尚未理解？ |
| 写代码 | 完成了功能、定位问题、验证方案，还是主要被打断？ |
| 打球 | 是否达到运动和放松目的？是否明显超出安排？ |
| 休息 | 得到恢复，还是在焦虑中反复刷手机？ |

### 7.3 数据边界

电脑自动采集的数据可参与问题生成。iPhone 常规使用报表仅作用户参照；没有截图导入或其他经验证的数据路径时，云端 AI 不知道报表里的具体时长，不能生成声称已经读取该数字的问题。

## 8. 热力图与统计口径

### 8.1 每日热力图

- 展示完整 24 小时，默认每格 15 分钟。
- 绿：利用较好；黄：一般；红：明显无意消耗；灰：未记录或信息不足。
- 点击查看活动、评分理由、数据来源和编辑入口。
- 睡眠和恢复可有图标或分类标签，不能因没有工作产出变红。
- 提供分数及文字标签，不只依赖红绿辨色。

### 8.2 精度规则

有明确分段的记录按真实边界映射；只有整个时段的比例或平均分时，只展示该段平均评价，并标为估计。不能把 30% 分心随意画到最后 30% 的时间。

混合格按记录覆盖时长计算；未知部分保留未知。区分记录覆盖率、平均评价和有效工作预算完成率，不将三者合并成一个含糊的数字。

### 8.3 多设备重叠

同一时间电脑和手机都有活动时，先按时间范围整合为证据，不相加为工作量。电脑前台论文窗口不等于用户专注；手机使用也不必然等于娱乐。

离开键鼠可能是在阅读、思考或纸上推导。只在影响评价时进行一次简短确认。

## 9. 日报与周报

### 9.1 日报

- 分类时间分布。
- 有效脑力工作时长、预算完成率。
- 主要目标投入情况。
- 一项做得好的事情。
- 一个可执行的小调整。
- 待补录或信息不完整提示。

### 9.2 周报

| 内容 | 输出 |
|---|---|
| 一周概览 | 七天热力图、记录覆盖率 |
| 时间分布 | 工作、运动、休息、娱乐、事务、无意消耗 |
| 工作投入 | 安排工作多久、实际有效投入多久 |
| 目标推进 | 主要目标投入、里程碑、DDL 风险 |
| 变化与进步 | 可比较条件下的增减、两三个具体进步 |
| 下周建议 | 一两个小目标，必要时建议调整优先级 |
| 鼓励文案 | 与事实相关的温和鼓励、吐槽、热梗或可靠引用 |

### 9.3 比较与文案

- 记录不完整时，不直接拿整周总量比较。
- 使用相同口径；规则或预算变化单独标出。
- 第一周缺少基线时不编造“提升百分比”。
- 改善可以体现为更少熬夜、更充分恢复，而不只是工作更多。
- 吐槽由用户开启，针对行为、不贬低人格。
- 新梗和真实名言需要适当核实；无法核实时用原创文案，不虚构署名。
- 联网检索属于可选能力，不是生成周报的必要条件。

## 10. 平台接入与明确边界

### 10.1 电脑：复用 ActivityWatch

复用前台应用、窗口标题、浏览器活动和空闲数据，通过本地 REST API 读取。先独立安装 ActivityWatch 与浏览器扩展，我们开发连接程序；后期再评估安装包整合。

连接程序负责：

- 查询用户选定的时间范围。
- 对齐前台窗口、网页、空闲事件。
- 应用忽略规则、域名或任务分类。
- 整理为时段摘要，而不是逐秒调用 AI。
- 区分原始记录、估计与用户确认的数据。

白名单、黑名单可按任务设置。浏览器、聊天软件均可能有工作用途，列表仅是判断依据之一。

不要将 ActivityWatch 本地服务直接暴露到公网。多人使用时，每台设备上的连接程序关联对应个人数据空间。

### 10.2 iPhone：报表与问答同屏

默认路径：

1. 用户授予个人 Screen Time 相关授权。
2. 主 App 选择时间范围和筛选条件。
3. 报表扩展展示设备使用情况。
4. 主 App 在同一页面接收自述、分类分配和问题答案。
5. 主 App 调用 API，保存最终记录并同步。

重要边界：

- 普通主 App 不能把常规报表中的原始使用时长直接当作自己的数据库输入。
- 报表扩展禁止联网及向外传递受保护使用数据；改成异步或共享文件不自动消除限制。
- 外部配置可尝试通过 App Groups 读取；Apple 工程师确认该方向应可用，需真机验证。
- 报表扩展可本地计算并显示统计，但不要依赖内部结果或交互自动回传主 App。
- 主 App 自己的问答控件接收的答案可以保存及调用 API。
- 常规路径不等于受欧盟条件限制的活动数据导出 API；不把后者作为通用依赖。
- 发布需要验证相关 entitlement 与分发流程。
- 纯网页或 PWA 不能完成原生 Screen Time 接入。

任意分钟级时间段的过滤效果、系统数据更新时间和统计精度须由原型验证；若系统粒度不匹配，明确标出参照报表实际覆盖范围。

截图由用户主动导入时可识别，但不作为每次记录的默认步骤。不依赖自动截图隔离报表实现数据导出。

### 10.3 Android：后续接入

用户授予使用情况访问权限后，可使用系统接口获取应用使用事件。精确时间范围需要处理事件边界，不能把整天聚合数据直接当作局部时段时长。

系统保留事件有时间限制，应及时保存需要的摘要。首次版本可只做手动记录和同步，后续再完成原生采集。

### 10.4 实验能力

| 能力 | 可以研究什么 | 不应承诺什么 |
|---|---|---|
| 使用阈值事件 | 选定应用累计达到某时长后辅助追问 | 任意历史时段的精确使用明细 |
| 加速度分析 | 平放、拿起、放下、疑似持续手持 | 可靠识别所有刷手机行为 |
| 手势采集 | 自己 App 内的触摸 | iPhone 全局读取其他 App 的滑动 |
| 主动屏幕分析 | 用户启动捕获后的活动线索 | 无感全天采集、恢复过去画面 |
| 本地 Agent | 用户设备运行的可选 AI 后端 | 任意订阅都可作为通用 API |

这些能力均不阻塞核心记录流程。需要真实设备和典型样本测试，尤其是无调试器、切换 App、锁屏、撤销权限等状态。

## 11. 系统架构

### 11.1 推荐基础形态

**本地存储优先，模型 API 与同步后端分离。**

每台客户端包含本地记录、统计与同步队列。没有网络时可正常记录；联网后执行模型任务及同步。基础个人版不强制依赖项目运营者的业务服务器。

| 模块 | 职责 |
|---|---|
| 桌面客户端 | 时间轴、编辑、回顾、ActivityWatch 集成 |
| iOS 客户端 | 原生报表、快速记录、问答与回顾 |
| 本地存储 | 记录、目标、规则、缓存、待执行任务 |
| 评分与统计模块 | 校验时长、计算指标、热力图聚合 |
| AI 适配层 | 模型能力、结构化输出、失败恢复 |
| 同步层 | 增量交换、去重、删除、冲突处理 |
| 可选服务端 | 托管版额度、集中代理、可靠定时任务 |

### 11.2 不强制自建账号

本地版先建立个人资料；跨设备通过配对或用户自己的云账号连接同一数据空间。自部署／托管多人版后续增加账号系统。

每个人使用独立数据空间，不把朋友、家人的私人记录放入同一个互相可读的数据仓库。

### 11.3 两种 AI 凭据路径

- 自带服务：用户在客户端安全配置 API 地址、模型、key，通过原生网络层调用；凭据不参与普通记录同步。
- 托管服务：运营者的 key 只在服务端，客户端通过受控接口调用并接受额度限制。

不将运营者的共享 key 内置到安装包或网页中。浏览器端直连涉及凭据和服务 CORS 等限制，不把它当作统一方案。

## 12. AI 调用契约

### 12.1 任务划分

1. `parse_entry`：整理描述、分类、关联目标，输出候选分配。
2. `prepare_review`：生成最多三项必要引导，常见流程可与整理任务合并调用。
3. `score_entry`：接收用户确认的事实，生成评分和理由。
4. `daily_review`：总结并提出规则调整建议。
5. `weekly_review`：周报、趋势解释、下周建议。

无需长期运行一个高频 Agent。普通程序负责时间计算、聚合与验证，AI 负责语义理解和解释。

### 12.2 调用原则

- 只发送当前任务必要的记录、目标、规则与少量相关历史。
- 不默认每次重发全部日记、原始窗口日志或附件。
- 配置文本、ASR、视觉等能力，支持不同服务分别承担。
- 使用结构化输出并做本地校验；不可用时采用受控解析与重试。
- 输出中的时长、比例、分数、分类 ID、目标 ID 需要校验。
- 附件与用户输入视为待分析数据，不允许其中的文字指令更改系统规则。
- 模型失败不影响原始记录保存；显示待分析、可重试与错误原因。
- 模型升级或更换记录版本，避免评分比较失去依据。

### 12.3 示例返回结构

```json
{
  "schema_version": 1,
  "entry_id": "entry_example",
  "score": {
    "execution_quality": 80,
    "goal_contribution": 90,
    "arrangement_quality": 70,
    "overall": 81,
    "reason": "关键实验有实质推进，中途存在一段未计划的分心。",
    "uncertainties": ["部分时间分配来自用户估计"],
    "rule_version": "rules_v1"
  },
  "suggestion": "下一段先明确一个实验里程碑，并安排一次主动休息。"
}
```

数值与权重仅为结构示例，不代表已确定的评分算法。整体分应依据版本化配置由程序计算，AI 不可绕开配置随意改权重。

## 13. 数据模型

所有同步对象至少包含稳定 ID、创建时间、修改时间、版本信息、来源设备和可同步的删除标记。时间点统一存 UTC，保留记录时区以重建当地日期。

| 对象 | 关键字段 |
|---|---|
| `Profile` | 个人 ID、时区、语言、显示偏好 |
| `TimeEntry` | 起止时间、原始描述、状态、任务意图、关联目标 |
| `Allocation` | 分类 ID、时长、估计／确认状态、可选具体子段 |
| `ReviewAnswer` | 问题、选项、答案、来源、记录版本 |
| `ScoreRevision` | 各维度、整体分、理由、AI 原始值、用户最终值、版本 |
| `Goal` | 层级、父目标、DDL、里程碑、进度、优先级 |
| `Category` | 名称、父分类、颜色、内置／自定义 |
| `RuleSet` | 配置、版本、生效时间、变更依据 |
| `WorkBudget` | 每日预算、生效范围、临时调整结束日期 |
| `EvidenceSummary` | 设备、时间范围、采集类型、聚合指标、可信范围 |
| `Attachment` | 类型、大小、引用、处理状态、保留策略 |
| `Report` | 日／周、覆盖范围、口径版本、统计、文本 |
| `SyncState` | 设备游标、待传队列、冲突、删除标记 |
| `AIJob` | 任务类型、输入版本、状态、幂等 ID、结果版本 |

主记录状态建议：`draft`、`pending_ai`、`needs_confirmation`、`confirmed`、`analysis_failed`。状态变化不得丢失用户输入。

用户可以修订已确认记录；对应日报和周报标记过期或按新输入版本重新生成。过时 AI 任务不得覆盖较新的手动修改。

## 14. 同步方案

### 14.1 同步协议与传输分离

先定义同步对象、版本、去重和冲突行为，再实现不同后端。网盘和 GitHub 只是传输／存储载体，不提供应用级语义合并。

- 离线创建和编辑进入本地待传队列。
- 新增、修改、删除均可增量交换。
- 重试使用稳定操作 ID，避免重复。
- 不仅凭设备本地时间判断最终版本，防止时钟偏差。
- 同一记录并发修改时保留两份候选，或做可解释的字段合并。
- 明确冲突处理，不能静默丢失答案或评分。
- 原始事实是权威数据；可重建的热力图和统计缓存无需作为冲突核心。

### 14.2 可选后端

| 后端 | 使用方式 | 特点 |
|---|---|---|
| 局域网 | 首次扫码配对，设备直接交换 | 无云依赖，但需要同时可达 |
| GitHub 私有仓库 | API 读写小文件与变更批次 | 适合开发者、低频小数据 |
| iCloud | CloudKit 等官方方案 | 优先服务 iPhone 与 Mac；跨平台另评估 |
| OneDrive | 应用专属目录 | 跨平台云中转 |
| Google Drive | 应用数据目录 | 跨平台云中转 |
| WebDAV | 对接用户已有存储 | 面向自托管用户，后续支持 |

一个数据空间首版只启用一个同步后端。后端迁移通过明确的导出／导入或迁移流程，避免多个云同时相互覆盖。

### 14.3 GitHub 首版实现建议

- 每个用户独立的私有数据仓库，与公开源代码仓库分开。
- 通过授权方式或最小权限凭据访问用户选定仓库。
- 同步结构化记录、规则、目标、报告；大型媒体与高频原始采集数据不放入常规提交。
- 采用小批次变更文件与定期快照；避免两台设备不断覆盖单一数据库文件。
- 基于远端版本条件更新；发生竞争后先拉取再合并。
- 打开 App、手动刷新或积累变化后批量同步，不逐秒提交。
- 若启用客户端加密，应有明确的跨设备密钥配对、备份与恢复流程。
- Git 历史可能保留旧数据；普通逻辑删除不等于彻底移除历史，需要单独说明与提供清理指导。

### 14.4 iCloud 实现边界

CloudKit 与“同步一个 iCloud Drive 文件夹”是不同方案，正式开发时选定其一并评估授权、数据模型、冲突和跨平台能力。不能假定 CloudKit 可直接套用 GitHub 的文件接口；可以共用领域对象和冲突策略，但后端适配有所不同。

### 14.5 后台和定时任务

- 数据同步不要求电脑全天开机；直连同步时双方需要在线。
- iPhone 先保证打开 App 或回前台时同步，不承诺无感即时后台同步。
- 云存储不执行 AI。无常驻后台时，日报周报在客户端获得执行机会时补生成。
- 多设备通过报告唯一键和任务幂等 ID 减少重复生成；仍需考虑并发时重复调用费用。
- 若以后要求固定时间生成与推送，再增加可选的服务端任务执行器。

## 15. 技术选型与仓库组织

### 15.1 选型原则

优先满足 iOS 原生报表、桌面本地 API、本地数据库和离线体验。先做两个薄客户端及明确数据契约，不为追求一套代码而牺牲平台能力。

可作为起点的方案：iOS 使用 SwiftUI 和原生扩展；桌面使用 Web UI 加原生桌面容器／本地连接程序。本地可采用 SQLite。具体框架版本在开工时锁定，桌面容器可先评估 Tauri 或 Electron，再依据团队熟悉程度决定。

第一版不要求 Swift 与桌面语言直接共享实现。共享 JSON Schema、接口定义、评分规范和验证样例；以后再评估跨语言共享库。

### 15.2 仓库建议

```text
apps/
  desktop/                 # 桌面界面与本地能力
  ios/                     # iOS 主 App
    ReportExtension/       # Screen Time 报表扩展
contracts/
  schemas/                 # 交换格式与 AI 输出结构
  fixtures/                # 跨平台统一验证样例
modules/
  scoring/                 # 评分规范与参考实现
  ai/                      # 模型适配、任务与提示词
  sync/                    # 同步协议与后端适配
integrations/
  activitywatch/           # 查询与数据整理
docs/
  product.md
  architecture.md
  scoring.md
  sync.md
  privacy.md
  platform-validation.md
```

这是逻辑组织建议，不暗示每个模块都能在所有语言中直接复用。

## 16. 隐私、数据拥有权与开源

- 原始记录默认留在设备；同步与 AI 上传都应有明确配置。
- 展示哪些信息会发往模型提供商，允许排除附件、应用标题、网站明细。
- 采集可暂停，可排除应用和网站。
- 允许导出人类可读的 Markdown／JSON，以及可恢复的完整数据备份。
- 删除与云端副本、Git 历史、附件保留等边界需要说明。
- 日志不记录 API key、授权 token、完整私人日记或敏感附件。
- 托管服务用户隔离，管理员不默认拥有浏览私人记录的产品入口。
- 无需为了使用基础功能向朋友索要模型账号密码或共享订阅凭据。
- 开源许可证待选定；复用 ActivityWatch 时保留归属并核对各实际组件的许可及分发义务。
- 先发布可理解的安装、权限、模型和同步配置文档，再增加高级功能。

## 17. 开发里程碑与验收

### P0：能力验证

- [ ] iPhone 真机完成个人授权和基础报表展示。
- [ ] 验证选定时间段与报表真实统计范围。
- [ ] 报表上方／下方的主 App 问答可以正常交互与保存。
- [ ] 验证从主 App 向报表扩展提供配置。
- [ ] 记录分发 entitlement 的申请与签名要求。
- [ ] ActivityWatch API 可以查询指定时间范围并得到活动摘要。
- [ ] 不依赖截图、报表回传或持续后台运行。

验收：得到可重复运行的小型原型，以及书面的能力边界。权限拒绝或报表失败时仍可手动记录。

### P1：本地记录闭环

- [ ] 时间段选择、输入、编辑、删除。
- [ ] 分类、分钟／比例换算、未知部分。
- [ ] 长短期目标与 DDL。
- [ ] 手动评分与本地保存。
- [ ] 每日热力图与有效工作统计。
- [ ] JSON 导出／导入。

验收：断网、重启后不丢数据；不用 AI 也能完成一天记录。

### P2：AI 评分闭环

- [ ] 可配置模型地址、模型与 key。
- [ ] 记录整理与最多三个问题。
- [ ] 结构化评分、理由、不确定项。
- [ ] 用户改分及原因。
- [ ] 失败重试、过期结果保护。

验收：模拟实际研究、娱乐、运动、休息场景，评分理由可理解；模型失败不阻塞保存。

### P3：设备参照

- [ ] 电脑 ActivityWatch 连接程序。
- [ ] 应用／网站忽略规则与任务相关分类。
- [ ] iPhone 报表同屏接入正式记录页。
- [ ] 设备来源标签、时间对齐、不重复计时。

验收：能够对照数据完成记录，不要求逐项核对；无权限和数据缺失时可继续使用。

### P4：一种同步后端

- [ ] 稳定 ID、变更队列、版本和删除标记。
- [ ] GitHub 私库或其他选定后端。
- [ ] 两端离线编辑后合并。
- [ ] 同步状态、冲突解决、重试与去重。
- [ ] 凭据安全存储；加密方案若启用则一并完成恢复验证。

验收：两台设备交替与并发编辑，不静默丢记录；失败可恢复。

### P5：复盘与个性化

- [ ] 日报与周报。
- [ ] 记录覆盖率、目标投入及同口径比较。
- [ ] 每日规则检查与版本化调整。
- [ ] 每周工作预算调整建议。
- [ ] 文案风格偏好。

验收：没有历史基线不编造进步；规则变化可解释；预算调整由用户确认。

### P6：开源发布

- [ ] README、截图或演示、安装和权限说明。
- [ ] 数据格式、备份恢复、同步配置和 AI 配置文档。
- [ ] 不含真实私人数据的示例记录。
- [ ] 许可证、第三方组件说明、贡献指南。
- [ ] 桌面安装包及 iOS 测试／分发路径说明。
- [ ] 已知限制、问题模板和后续路线。

验收：新用户能根据文档完成首次记录与备份；本地模式不强制注册服务。

## 18. 必要测试范围

重点测试会造成时间统计错误、数据丢失或隐私泄露的路径，不为每个简单 UI 细节堆测试。

## 20. MVP 完成标准

第一版至少能让用户完成以下一天：

1. 设置一个短期目标和 DDL。
2. 在手机或电脑补录几个活动段。
3. 对照可用设备参照，回答两三个问题并分配时间。
4. 获得能理解、能修改的评分。
5. 查看没有虚假精度的 24 小时热力图。
6. 在另一台设备看到已同步记录。
7. 一周后看到有依据的统计、进步和下一周建议。
8. 导出并恢复自己的数据。

产品成功不以记录数量或工作小时越多越好衡量，而以记录负担低、评价可信、能够持续使用并帮助用户调整生活为准。
